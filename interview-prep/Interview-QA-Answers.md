## Core C# / .NET

**1. Explain what happens under the hood with async/await — does it create a new thread?**
No — async/await doesn't inherently create a thread. When you await a `Task`, the compiler generates a state machine that pauses the method at that point and returns control to the caller. The actual work (e.g. an I/O call like a DB query or HTTP request) runs on the OS/driver level asynchronously, often using I/O completion ports, not a dedicated thread. Once the awaited operation completes, the continuation resumes — in classic ASP.NET/UI apps it resumes on the captured `SynchronizationContext` (the UI thread, for example); in ASP.NET Core there's no sync context, so it resumes on any available thread-pool thread. The main benefit is that the original thread is freed to handle other work while waiting, which is why async matters for scalability under load, not for CPU-bound parallelism (for that you'd use `Task.Run` or `Parallel`).

**2. Difference between IEnumerable and IQueryable — why does it matter when querying via EF?**
`IEnumerable` represents an in-memory sequence — LINQ operators on it execute against objects already loaded into memory using compiled .NET delegates. `IQueryable` builds an expression tree that a provider (like EF Core) translates into SQL and only executes when enumerated. The practical trap: if you write `dbSet.AsEnumerable().Where(x => x.Name == name)`, the `Where` runs in memory after pulling the entire table across the wire, whereas `dbSet.Where(x => x.Name == name)` on an `IQueryable` gets pushed down into a `WHERE` clause in SQL. I always double check where in a LINQ chain I've accidentally dropped from `IQueryable` to `IEnumerable`, since it silently changes where computation happens.

**3. Explain DI lifetimes (Transient, Scoped, Singleton) and describe a captive dependency bug.**
Transient creates a new instance every time it's resolved. Scoped creates one instance per HTTP request (or per scope you create manually) — this is what I use for things like `DbContext` and repositories, since I want consistent state within a single request but not shared across requests. Singleton creates one instance for the lifetime of the application. A captive dependency happens when a longer-lived service holds a reference to a shorter-lived one — e.g. injecting a Scoped `DbContext` into a Singleton service. The DbContext gets captured at first resolution and then reused for the app's entire lifetime, way outside its intended request scope, which causes stale data, threading issues, or an exception depending on configuration. The fix is either to make the dependency Scoped too, or inject `IServiceScopeFactory` into the singleton and create a fresh scope per operation.

**4. When would you use a record instead of a class?**
Records are a good fit for immutable data models — DTOs, value objects, anything where equality should be based on the values inside rather than reference identity. `record` gives you value-based `Equals`/`GetHashCode` and a concise `with` expression for non-destructive mutation, all generated by the compiler. I'd use a class instead when the type has real identity and mutable state over its lifetime — like an EF entity that's tracked and updated across its life in the database, where reference equality and change tracking matter more than value equality.

**5. What's the difference between Task.Wait()/.Result and await, and why can mixing them deadlock?**
`.Wait()`/`.Result` block the calling thread until the task completes. `await` doesn't block — it yields control back to the caller. The deadlock scenario happens in environments with a `SynchronizationContext` (classic ASP.NET MVC, WPF, WinForms): if a UI/request thread calls `.Result` on a task, it blocks that thread while waiting. If the awaited async method later tries to resume on that same captured context, it can't, because the very thread it needs is the one that's blocked waiting on it — classic deadlock. ASP.NET Core doesn't have that sync context by default, so this specific deadlock is less common there, but it's still bad practice — it defeats the whole point of async and can exhaust the thread pool under load.

**6. Explain covariance and contravariance with a generic interface example.**
Covariance (`out T`) lets you use a more derived type than originally specified — `IEnumerable<out T>` means an `IEnumerable<Dog>` can be used where `IEnumerable<Animal>` is expected, because you're only ever reading `T` out of it. Contravariance (`in T`) lets you use a less derived type — `IComparer<in T>`, an `IComparer<Animal>` can be used where `IComparer<Dog>` is expected, because the comparer only ever receives `T` as input, never returns it. The rule of thumb: `out` for types you only produce/return, `in` for types you only consume/accept as parameters.

## Entity Framework

**7. What's the N+1 query problem and how have you fixed it in a real project?**
It's when you run one query to get a list of entities, then loop over that list and trigger a separate query per row to fetch related data — 1 query becomes N+1. It usually happens with lazy loading, where accessing a navigation property inside a loop silently fires a new query each time. In my own project, staff records needed their branch info, so instead of looping and lazy-loading `staff.Branch` per row, I used eager loading with `.Include(s => s.Branch)` on the initial query, turning N+1 queries into a single query with a join.

**8. When would you use .AsNoTracking(), and what's the tradeoff?**
I use it for read-only queries — GET endpoints that return data but never update it in the same request. It skips EF's change tracker, which normally snapshots entity state to detect what changed for `SaveChanges`. Skipping that bookkeeping is measurably faster and uses less memory, especially for larger result sets. The tradeoff is you lose the ability to modify and save that entity later in the same context — if you need to update it, you'd have to re-attach and mark it modified, so it's specifically for the "read and return" path, not anything you intend to mutate.

**9. Eager vs lazy vs explicit loading — pros and cons of each.**
Eager loading (`.Include()`) loads related data in the same query — predictable, good for known access patterns, but can over-fetch if you don't need the related data every time. Lazy loading loads related data automatically the first time a navigation property is accessed, via runtime proxies — convenient, but easy to accidentally trigger N+1 problems, especially during serialization when a whole object graph gets walked. Explicit loading (`context.Entry(x).Reference(y).Load()`) gives you manual control to load related data only when you decide to — more verbose, but predictable and avoids hidden queries. In API code I generally prefer eager or explicit over lazy, specifically to avoid surprise queries.

**10. How do EF migrations work in a CI/CD pipeline with multiple running instances?**
Migrations are applied via `dotnet ef database update` (or `Database.Migrate()` in code) which runs pending migration scripts against the target database. In a pipeline, I'd run migrations as a distinct, single deploy step — not inside app startup — specifically to avoid a race where multiple app instances spin up simultaneously and all try to apply the same migration at once. If migrations must run at startup, you need some form of distributed lock or a leader-election step so only one instance applies them while the others wait.

**11. How do you handle optimistic concurrency conflicts in EF?**
Add a concurrency token — typically a `[Timestamp]`/`rowversion` column — to the entity. EF includes that column's original value in the `WHERE` clause of the generated `UPDATE`. If another process changed the row in between, zero rows match and EF throws `DbUpdateConcurrencyException`. In the catch block, you decide the resolution strategy — reload the current DB values and let the user re-apply their change (client wins after review), overwrite with the client's version regardless (client wins silently), or merge field by field.

## SOLID / Design Patterns

**12. Give a real example from your own code where you applied Single Responsibility or Dependency Inversion.**
In my travel booking project, `AuthService` only handles authentication — validating credentials and issuing JWTs — while `StaffService` handles staff CRUD, and they don't overlap. For dependency inversion, my controllers depend on interfaces like `IBookingService`, not the concrete `BookingService` class, injected via the DI container — so the controller has no idea which implementation it's actually talking to, which makes it trivial to swap in a mock for unit testing or a different implementation later without touching the controller.

**13. What's wrong with a Square class inheriting from Rectangle? (Liskov)**
`Rectangle` typically exposes independent `SetWidth`/`SetHeight`. If `Square` inherits from it but overrides those setters to keep width and height equal (since a square must have equal sides), it breaks the base type's contract — code that expects "setting width doesn't affect height" now behaves unexpectedly when handed a `Square` through a `Rectangle` reference. That violates Liskov substitution: a subtype should be usable anywhere its base type is expected without surprising behavior.

**14. When would you reach for the Strategy pattern instead of a big if/else or switch?**
When you have a family of interchangeable algorithms or behaviors selected at runtime, and the conditional logic keeps growing every time a new case is added. Instead of one method with a long if/else picking behavior by type or flag, you define a common interface, implement each variant as its own class, and inject or select the right one at runtime. It keeps each behavior isolated and testable on its own, and adding a new case means adding a new class rather than editing a growing conditional — Open/Closed principle in practice.

**15. What's the criticism of layering a Repository pattern on top of EF's DbContext?**
`DbContext` and `DbSet<T>` already implement the Repository and Unit of Work patterns internally — `DbSet<T>` is essentially a repository, and `SaveChanges()` is the unit-of-work commit. Adding a custom `IRepository` wrapper on top can be redundant ceremony that doesn't add real abstraction, since it's still fundamentally coupled to EF underneath, and it can hide useful EF-specific features (like `.Include()` chaining or compiled queries) behind an overly generic interface. That said, a thin repository layer can still be worth it for testability (mocking an interface is simpler than mocking `DbContext`) or if you genuinely might swap data-access technology later — so my honest take is "it depends on the value the abstraction buys you, not a blanket rule."

## API Design & Testing

**16. How do you approach versioning a public API?**
A few options depending on constraints: URL segment versioning (`/api/v1/...`) is the most explicit and cache-friendly; header-based versioning keeps URLs clean but is less discoverable; query-string versioning is simplest but least conventional. I lean toward URL segment versioning for public APIs since it's unambiguous and easy for consumers to pin to, and I'd only introduce a new version when there's a genuine breaking change — additive, backward-compatible changes don't need a version bump.

**17. How would you unit test a controller that depends on a service interface?**
Mock the interface — with Moq, create a `Mock<IBookingService>`, set up `.Setup(s => s.GetBookingByIdAsync(id)).ReturnsAsync(fakeBooking)`, then construct the controller with that mock injected via its constructor. Call the action method directly, and assert on the returned `ActionResult` — check it's the expected result type (`OkObjectResult`, `NotFoundResult`) and that the wrapped value matches what you expect. This isolates the controller's logic from the actual service/database entirely.

**18. Difference between unit and integration tests in ASP.NET Core, and when do you use WebApplicationFactory?**
Unit tests isolate a single class, mocking out its dependencies — fast, no real infrastructure. Integration tests exercise multiple layers together — routing, middleware, DI, sometimes a real or in-memory database — to verify they work correctly as a whole. `WebApplicationFactory<TEntryPoint>` spins up your actual app in memory, including the full middleware pipeline, and gives you an `HttpClient` to hit real endpoints against it. I'd use it to verify things unit tests can't catch — like confirming `ExceptionHandlingMiddleware` actually returns the right JSON shape and status code end-to-end, or that auth middleware correctly blocks an unauthenticated request.

**19. How would you diagnose and fix a slow API endpoint in production?**
Start with observability — logs, APM traces (App Insights, or Splunk in this role's stack), to see where time is actually going: is it the DB query, an external call, serialization, or something CPU-bound. If it's DB-related, I'd check the actual generated SQL and execution plan, look for missing indexes or N+1 patterns. If it's a large payload, consider pagination or projecting to a smaller DTO instead of returning full entity graphs. I'd also check if the endpoint is doing synchronous blocking I/O instead of async, and confirm caching is being used where the data doesn't change per request. Fix, then verify with the same tracing/monitoring to confirm the change actually moved the needle rather than assuming it did.

## Angular

**20. Walk me through how a route guard works — what does canActivate actually check?**
`canActivate` is a property on a route definition that Angular's router checks before it renders that route's component. You give it one or more guard functions (or, in the older API, classes implementing `CanActivate`); the router calls each one, and if any returns `false` (or a redirect `UrlTree`), navigation is blocked and that guard is responsible for deciding what happens instead — typically redirecting elsewhere. I built one recently as a functional guard (`CanActivateFn`) that checks `localStorage` for an auth token: if present, it returns `true` and the route loads; if not, it calls `router.navigate(['/'])` to send the user to login and returns `false` to stop the original navigation.

**21. Structural vs attribute directives — give an example of each.**
Structural directives change the DOM's structure — adding, removing, or repeating elements — and are prefixed with `*`, like `*ngIf` (conditionally renders an element) or `*ngFor` (repeats an element per item in a collection). Attribute directives change the appearance or behavior of an existing element without altering the DOM structure — like `ngClass` (toggles CSS classes) or `ngStyle` (applies inline styles conditionally), or a custom one you write yourself to, say, highlight an element on hover.

**22. Pure vs impure pipes — why does it matter for performance?**
Pure pipes (the default) only re-execute when Angular detects the input reference has changed — so if you pass the same array reference into a pipe repeatedly even if its contents mutated internally, the pipe won't re-run, keeping change detection cheap. Impure pipes re-run on every single change detection cycle, regardless of whether the input actually changed — necessary for things like filtering a mutable array in place, but expensive if overused, since it runs constantly rather than only when something meaningfully changed. Performance-wise, default to pure pipes and only mark one impure when you have a specific reason.

**23. Default vs OnPush change detection — when would you switch to OnPush?**
Default change detection checks every component in the tree on every change detection cycle, triggered by almost anything (DOM events, timers, HTTP responses). `OnPush` tells Angular to only re-check a component when one of its `@Input` references changes, an event originates from within the component itself, or you manually call `markForCheck()`/`detectChanges()` — Observables via the async pipe handle this automatically too. I'd switch to OnPush for components deep in a large tree that render often but rarely actually change, especially list items, to cut down on unnecessary check cycles — it's a meaningful performance lever in larger apps.

**24. Explain the NgRx data flow: action → reducer → effect → selector.**
A component dispatches an `Action` — a plain object describing what happened, like `loadBookings()`. The `Reducer`, a pure function, takes the current state and that action and returns a new state object — for a synchronous state change like "set loading to true." If the action needs a side effect, like an HTTP call, an `Effect` listens for that action via the `Actions` stream, performs the async work, and dispatches a new action with the result (success or failure) once it resolves — the effect itself never touches state directly. A `Selector`, often memoized via `createSelector`, reads a specific slice of state back out for components to subscribe to via the `Store`. So the loop is: dispatch → reducer updates state synchronously and/or effect handles async work and dispatches again → selector exposes the updated slice back to the UI.

**25. When would you choose NgRx over a shared service with a BehaviorSubject?**
NgRx earns its complexity when state is shared across many unrelated parts of the app, has non-trivial derived/computed values, needs strict traceability of what changed and why (time-travel debugging, action logs), or when multiple developers need a consistent, enforced pattern for how state changes happen. For smaller apps or state that's local to a feature, a shared service wrapping a `BehaviorSubject` is often simpler, faster to write, and easier to reason about — I'd rather be honest that I'd choose the simplest tool that fits the actual complexity of the state, not reach for NgRx by default.

**26. How does the async pipe help avoid subscription memory leaks?**
Manually calling `.subscribe()` in a component means you're responsible for calling `.unsubscribe()` in `ngOnDestroy`, or the subscription (and anything it's holding a reference to) can outlive the component, causing a memory leak and potentially stale callbacks firing after the component's gone. The `async` pipe (`observable$ | async` in the template) subscribes automatically when the component initializes and unsubscribes automatically when the component is destroyed, so you never have to manage that lifecycle by hand — one less place for a leak to sneak in.

**27. What's the difference between Jasmine and Karma?**
Jasmine is the testing framework — it provides the syntax and assertion library: `describe` blocks group related tests, `it` defines individual test cases, `expect().toBe()` etc. make assertions, `spyOn` creates spies/mocks. Karma is the test runner — it launches a real browser (or headless Chrome), runs the compiled test files in it, and reports pass/fail results back to the terminal or CI pipeline. So Jasmine defines *what* a test looks like, Karma is *how* it actually gets executed and results collected.
